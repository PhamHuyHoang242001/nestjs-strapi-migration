## Findings (9)

### F1 — Seeder is INSERT-ONLY; it will NEVER emit the 8 new codes at existing ids. [CRITICAL]
Location: phase-01 §Implementation step 2 + step "44 → repurpose"; §Success "BI_PAYMENT_PROGRAM có đúng 8 items".
Flaw: Plan assumes editing `BI_PAYMENT_PROGRAM` array reseeds codes. `permission.seeder.ts:350-351` computes `toInsert = dataConfig.filter(!existingIds.has(id))` and at :351 `if (!toInsert.length) return;`. It NEVER UPDATEs an existing row's code/name/action. Ids 39-42 already exist → they keep old rows untouched (fine, unchanged). But ids 49/52/53/54 for the *new* codes: if the migration cleanup DELETEs 43-48 and the seeder runs, only truly-absent ids insert — OK for brand-new ids. However the plan's alternative "repurpose id 44 → upload" (phase-01 §Architecture, line 23) is a silent no-op: 44 exists post-migration only if not deleted; if kept, seeder skips it and code stays `bp_program_preparing`. Gate `bp_program_upload` then resolves to a permission row that does not exist → every upload user 403s.
Failure scenario: deploy runs, admin grants "Upload" role, users still can't upload because code `bp_program_upload` was never inserted (id 44 kept its old code) OR was inserted but data_access rules reference a stale id.
Evidence: `src/seeders/permission.seeder.ts:350-356` (insert-only, early return, no update path).
Fix: Either (a) migration itself INSERTs the 8 new rows + UPDATEs/DELETEs old, treating seeder as irrelevant for prod; or (b) rewrite seeder to upsert (ON CONFLICT DO UPDATE) code/name/action. Decide ONE source of truth. Phase 1 must not rely on the current insert-only seeder to mutate existing ids.

### F4 — Migration DELETE targets WRONG table names → migration fails or no-ops, leaving orphan data_access rows. [CRITICAL]
Location: phase-01 §Implementation step 3.
Flaw: Plan writes `DELETE FROM data_access_users WHERE permission_id IN (43..48)` and "tương tự role_data_access". Actual schema: `data-access.entity.ts:46` puts `permission_id` on the **`data_access`** table (Entity `data_access`, line 9), NOT on `data_access_users` (line 37, which has user_id/data_access_id only) and NOT on a table called `role_data_access` — the real join table is `data_access_roles` (line 61). So `DELETE FROM data_access_users WHERE permission_id...` fails (no such column) and `role_data_access` does not exist.
Failure scenario: migration `up` throws at runtime on prod → half-applied state (some deletes done, permissions still present or FK-violation). Rollback of a partial migration is undefined.
Evidence: `data-access.entity.ts:9` (`@Entity('data_access')`), `:37` (`data_access_users`), `:46` (`permission_id` lives on `data_access`), `:61` (`data_access_roles`). Plan phase-01 line 44 uses `data_access_users`/`role_data_access`.
Fix: DELETE from `data_access WHERE permission_id IN (...)` (cascade to `data_access_users`/`data_access_roles` via data_access_id) + `role_permissions WHERE permission_id IN (...)`. Plan's own note "xác nhận tên bảng thực tế" is correct but the drafted SQL is already wrong — verify BEFORE writing, not after.

### F5 — Migration-then-reseed deploy ordering leaves a lockout + stale-cache window; no cache invalidation anywhere. [CRITICAL]
Location: phase-06 §Implementation step 3 (rollout order: "migration cleanup → seed code → restart → admin gán"); phase-01 §Non-functional.
Flaw #1 (state gap): Between `migration cleanup` (deletes 43-48 + data_access rows) and `admin re-grants roles`, NO user has any bi-payment step permission. Every doc/template list throws `ForbiddenException` (step-scope resolves empty → `step-scope.service.ts:51`). This is an authorization outage of unknown duration (manual admin work). Plan acknowledges "downtime quyền" (phase-06 risk) but rollout doesn't gate app traffic — users hit 403 storms, not a maintenance page.
Flaw #2 (stale cache): `getAccessibleRecords` and `getPermissions` are Redis-cached (`permission-cache.service.ts:52-68`, `:19-35`, TTL-based). After codes are deleted/reseeded and roles re-granted, cached entries for old codes/permission-sets persist until TTL. NO seeder/migration calls `invalidateAll()` / `invalidateByTable('bi_payment_programs')` — grep of `src/seeders` + `src/migration` for `invalidate` returns nothing. A user who was cached before re-grant keeps stale (empty or old) accessibleRecords → sees nothing or sees stale programs after admin grants.
Failure scenario: admin grants "Upload" role at T; user still 403s until Redis TTL expires (could be minutes), files a bug, ops "can't reproduce" after TTL lapses. Classic heisenbug.
Evidence: `permission-cache.service.ts:52-68` (cached, no post-seed hook); grep `invalidate` in seeders/migration = 0 hits; `step-scope.service.ts:51` (empty scope → Forbidden).
Fix: rollout checklist MUST include an explicit `invalidateAll()` (or Redis FLUSH of `perm:user:*`) step AFTER admin re-grants and BEFORE opening traffic. Add maintenance-gate. Sequence: maintenance ON → migrate → restart → admin grant → cache invalidate → smoke → maintenance OFF.

### F7 — Dual resolver drift: `resolveAllowedWorksteps` (Set, 8 call-sites) vs new `resolveWorkstepScopes` (Map, own-aware) can disagree; single-doc asserts keep the Set path and leak/over-block. [HIGH]
Location: phase-02 §Architecture (keep both APIs), phase-04 §Architecture step (checkDocStep/assertDocStep use resolveWorkstepScopes).
Flaw: Plan keeps `resolveAllowedWorksteps` deriving `new Set(map.keys())` (phase-02 step 2) — this DROPS the `own` flag. 8 live call-sites use the Set form: `document.service.ts:67,188,314,539` and `template.service.ts:84,212,404,412`. Two of these are SECURITY asserts for single records: `checkDocStep` (:539, backs `findOne`/`download`/`updateStatus`/`uploadStatus`) and template `assertTemplateStep` (:404). If phase-04 migrates `list` (:67) to own-aware Map but leaves `checkDocStep` (:539) on the own-blind Set, then: a recon-only user's `list` correctly hides other users' RECON_DATA, but `download/:id` (via checkDocStep→resolveAllowedWorksteps→Set contains RECON_DATA because the workstep key IS present with own:true) returns TRUE → **direct-id download of another user's recon doc succeeds**. The Set says "you can see RECON_DATA at this program" (true, own-scoped) but loses "only your own". Phase-04 step 4 vaguely says checkDocStep "cập nhật dùng resolveWorkstepScopes" but doesn't specify the own-filter must be applied per-doc (compare `doc.uploaded_by_id === userId`).
Failure scenario: IDOR — recon uploader B GETs `/document/{A's recon doc id}/download` → 200, data leak. The list hides it but the detail endpoint doesn't.
Evidence: `step-scope.service.ts:34-53` (Set derivation loses own); `bi-payment-document.service.ts:539` (`checkDocStep` uses Set), consumed by `findOne` (:287), `download` (:293), `updateStatus` (:392), `uploadStatus` (:228).
Fix: phase-04 MUST specify checkDocStep/assertDocStep compare `doc.uploaded_by_id` when the resolved scope for that workstep is `own:true`. Add an explicit success criterion + security test for cross-user single-doc download (phase-05 §Security has the list case but the report must add the DETAIL/DOWNLOAD-by-id case).
