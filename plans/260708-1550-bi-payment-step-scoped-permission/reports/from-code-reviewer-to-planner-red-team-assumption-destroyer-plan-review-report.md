## Finding 1: No operational path to create program-level data_access rules — non-SO users get blank screens
- **Severity:** Critical
- **Location:** plan.md L23-26 ("Reuse 100% plumbing... role/user-exception = code effective only at programs with data_access rule"); phase-02 L31-33
- **Flaw:** Plan claims "reuse 100% plumbing, no migration, no table new" but the plumbing only READS `data_access` rows. For a rule to scope a code to `programId`, someone must CREATE `data_access` rows with `data_id=programId` AND `module_id=13` (bi_payment_programs module). The seeder (`src/seeders/data-access.seeder.ts:14-27`) only creates rows for `module_id` 3, 4, 7 — NONE for module_id 13. There is no admin UI / endpoint shown in the plan to create program-scoped rules. Result: in any environment without manual SQL inserts, `getAccessibleRecords(userId, 'bi_payment_programs', code)` returns `[]` for every non-SO user → `resolveAllowedWorksteps` throws `ForbiddenException` → list-doc 403 for ALL non-SO users regardless of role assignment.
- **Failure scenario:** Role "Sale Recon" is created with `bp_program_reconciliation_sale` permission and assigned to user. User opens list-doc?programId=5 → verb gate passes (code in role.permissions) → `resolveAllowedWorksteps` calls `getAccessibleRecords(userId, 'bi_payment_programs', 'bp_program_reconciliation_sale')` → returns `[]` (no data_access row links user's role to programId=5 via module_id=13) → `allowed.size === 0` → throws 403. User sees nothing despite having the role. Regression vs current behavior (where `@RequireDataAccess(TABLE)` + `applyDataScope` also depends on the same missing rows, but current path at least returns empty list, not 403).
- **Evidence:** Plan L23 "role/user-exception = code effective only at programs with data_access rule"; `src/seeders/data-access.seeder.ts:14-27` (module_id 3,4,7 only); `src/seeders/module.seeder.ts:128` (module_id 13 = bi_payment_programs); `src/common/authorization/services/permission-query.service.ts:165-169` (join `m.table_name = :tableName` — returns nothing if no data_access row for that table).
- **Suggested fix:** Plan must add a phase (or explicit prerequisite) for (a) seed data creating data_access rows for bi_payment_programs, OR (b) document the admin endpoint/UI that creates such rules, OR (c) explicitly state this plan ships enforcement-only and rule creation is a separate operational task — and add a runtime guard: if `getAccessibleRecords` returns empty for ALL codes AND user is not SO, return empty list (not 403) to avoid breaking existing screens until rules are provisioned.

## Finding 2: `programUnderOwnedRoots` duplicates existing `isInOwnedScope` — reinvents tested helper
- **Severity:** High
- **Location:** phase-01 L24 ("programUnderOwnedRoots: query program's bicc_department_id, check ∈ ownedRootIds"); phase-02 L28 ("isOwner = await programRepo.biccDeptOf(programId) ∈ ownedRoots"); brainstorm L72
- **Flaw:** `OwnerScopeResolverService.isInOwnedScope(userId, tableName, recordId)` already walks the hierarchy chain from any table up to its root and checks against ownedRootIds. For bi_payment_programs it walks program→project→bicc_department (2 hops) and checks `bicc_department.id = ANY(ownedRootIds)`. The plan proposes a custom `programRepo.biccDeptOf(programId)` query + manual set membership check — duplicating logic that already exists, is tested, and handles soft-deletes + chain validation.
- **Failure scenario:** Plan's custom `biccDeptOf` query is written ad-hoc. If it forgets `deleted_at IS NULL` on project or bicc_department join (which `isInOwnedScope` enforces at L214), a soft-deleted project would still match → SO owner of a deleted bicc dept sees programs they shouldn't. Or if hierarchy-config changes (e.g. program gains direct bicc_department_id), the custom query breaks while `isInOwnedScope` auto-adapts.
- **Evidence:** `src/common/authorization/services/owner-scope-resolver.service.ts:185-231` (full `isInOwnedScope` impl with chain walk + soft-delete guards); `src/modules/data-access/__tests__/owner-scope-helpers.spec.ts:33` (`findRootTable('bi_payment_programs')` = `bi_hub_bicc_departments`); plan phase-02 L28 proposes `programRepo.biccDeptOf(programId) ∈ ownedRoots`.
- **Suggested fix:** Replace `programUnderOwnedRoots` / `biccDeptOf` with `ownerScope.isInOwnedScope(userId, 'bi_payment_programs', programId)`. Drop the custom query entirely. This also removes the need to inject `programRepo` into `StepScopeService`.

## Finding 3: DTO field name mismatch — plan renames `workstep` to `workstepType`, breaking existing clients
- **Severity:** High
- **Location:** phase-03 L29 ("workstepType = q.workstepType (optional, @IsEnum(MaToolWorkstepType))"); phase-03 L47 ("thêm `workstepType?: MaToolWorkstepType`")
- **Flaw:** Current DTO field is `workstep` (string), not `workstepType`. Current service reads `query.workstep` and filters `t.workstep_type = :wt`. Plan renames to `workstepType` and changes type to enum. This is a silent breaking change to the query contract: existing clients sending `?workstep=prepare` will hit a DTO that no longer recognizes `workstep` (validation strips unknown props depending on `whitelist`/`forbidNonWhitelisted` config) → filter silently dropped → returns ALL allowed worksteps instead of the requested one.
- **Failure scenario:** Client (Strapi parity consumer) calls `GET /bi-payment/document?programId=5&workstep=recon_data`. New DTO has `workstepType` only. `workstep` is ignored. Service receives `workstepType=undefined` → takes the "no workstepType" branch → returns union of all allowed worksteps. Sale user expecting only recon_data docs now sees prepare/ex_prepare docs too (if they have those codes) — data leak across workstep boundary.
- **Evidence:** `src/modules/bi-payment/document/dto/search-bi-payment-document.dto.ts:66` (`readonly workstep?: string;`); `src/modules/bi-payment/document/bi-payment-document.service.ts:52` (`if (query.workstep) qb.andWhere('t.workstep_type = :wt', { wt: query.workstep });`); plan phase-03 L29 uses `workstepType`.
- **Suggested fix:** Keep `workstep` as the DTO field name (backward compat) OR add `workstepType` as alias while keeping `workstep`. If rename is intentional, plan must explicitly call out the breaking change in phase-03 Risk Assessment and require client migration. Current phase-03 L77 only flags `programId` required as breaking — misses the field rename.

## Finding 4: `programId` DTO type mismatch — plan assumes number, DTO is string
- **Severity:** High
- **Location:** phase-03 L27 ("programId = q.programId (required, DTO @IsNumber)"); phase-03 L62 ("programId `@IsNumber()`, `@IsNotEmpty()`")
- **Flaw:** Current DTO declares `programId?: string` (not number). Controller coerces via `Number(q.programId)`. Plan says "DTO @IsNumber" — changing the type to number will break the existing string-based coercion path. Worse, if `@IsNumber()` is added and client sends `?programId=5` (query string, always string), class-validator rejects it → 400 for ALL clients. Query params are strings by default in NestJS; `@IsNumber()` on a query param requires `@Type(() => Number)` from `class-transformer`.
- **Failure scenario:** Client calls `GET /bi-payment/document?programId=5`. DTO has `@IsNumber()` on `programId`. class-validator sees string "5" → fails `isNumber` → 400 Bad Request. Every list-doc call breaks.
- **Evidence:** `src/modules/bi-payment/document/dto/search-bi-payment-document.dto.ts:21` (`readonly programId?: string;`); `src/modules/bi-payment/document/bi-payment-document.controller.ts:34` (`const programId = q.programId ? Number(q.programId) : undefined;`); plan phase-03 L62.
- **Suggested fix:** Keep `programId` as `@IsString()` + `@IsNotEmpty()` in DTO, coerce to number in controller/service (`Number(programId)`). OR use `@Transform(({ value }) => Number(value), { toClassOnly: true })` + `@IsNumber()`. Plan must specify the exact validation decorator stack — current "DTO @IsNumber" is underspecified and will break.

## Finding 5: Phase 3 references non-existent module file `bi-payment-document.module.ts`
- **Severity:** High
- **Location:** phase-03 L49 ("Modify: `src/modules/bi-payment/document/bi-payment-document.module.ts` (import StepScopeModule)")
- **Flaw:** No such file exists. The document controller/service are registered directly in `bi-payment.module.ts`. There is no per-feature module file. Following the plan's instruction literally, the implementer would create a new file `bi-payment-document.module.ts` — introducing a redundant module that conflicts with the existing registration in `bi-payment.module.ts`, causing a "duplicate provider" NestJS error.
- **Failure scenario:** Implementer creates `bi-payment-document.module.ts` per plan, imports `StepScopeModule` there, and adds it to imports — but the document controller is already declared in `BiPaymentModule`. NestJS throws "BiPaymentDocumentController is already registered" or StepScopeModule isn't visible to the document service because the new module isn't wired into the actual module graph.
- **Evidence:** `find` returns no `bi-payment-document.module.ts`; `src/modules/bi-payment/bi-payment.module.ts:22-23` (controller + service registered directly); `src/modules/bi-payment/bi-payment.module.ts:40-54` (TypeOrmModule.forFeature includes BiPaymentDocument).
- **Suggested fix:** Phase 3 must say "Modify: `src/modules/bi-payment/bi-payment.module.ts` — add `StepScopeModule` to imports, add `StepScopeService` to providers (or ensure StepScopeModule exports it)". Delete the reference to the non-existent file.

## Finding 6: Test convention claim is stale — plan bases test strategy on wrong memory
- **Severity:** Medium
- **Location:** phase-02 L20 ("theo memory convention `perm-real-db-integration-test-convention` — perm tests = DB-mocked, assert emitted SQL shape / mock return")
- **Flaw:** The plan cites memory `perm-real-db-integration-test-convention` (DB-mocked). But memory `group-role-bulk-sync-shipped` says "enabled real-DB e2e harness (orm.config JEST_WORKER_ID branch)". Verification of actual test files shows: `orm.config.ts:12` branches on `JEST_WORKER_ID` for entity loading paths (TS vs dist), NOT for connecting to a real DB. The only DataSource instantiation in specs (`so-owner-scope-integration.spec.ts:227`) uses `entities: [], synchronize: false` — a stub for `getQueryAndParameters()`, NOT a real connection. So the "real-DB e2e harness" memory is either stale or refers to a different mechanism. The plan's DB-mocked convention claim happens to match reality, but the plan doesn't verify — it trusts a memory that conflicts with another memory.
- **Failure scenario:** Implementer reads both memories, gets confused, attempts to write a real-DB integration test (per group-role-bulk-sync memory), fails to connect (no test DB configured), wastes time. Or worse: implementer writes tests assuming real-DB semantics, then tests pass in mock but fail to catch a real SQL bug (e.g. the `biccDeptOf` join emitting wrong column names).
- **Evidence:** `src/configuration/orm.config.ts:12` (JEST_WORKER_ID only switches entity glob, not connection); `src/common/authorization/__tests__/so-owner-scope-integration.spec.ts:227` (`new DataSource({ type: 'postgres', entities: [], synchronize: false })` — no `.initialize()`); no `createConnection` or `.initialize()` in any spec.
- **Suggested fix:** Plan should explicitly state: "Test strategy: DB-mocked composition specs (verified: no real-DB harness exists in this repo; `orm.config.ts` JEST_WORKER_ID branch only switches entity paths). Assert emitted SQL shape via `getQueryAndParameters()` + mock return values." Drop the memory citation — verify against code instead.

## Finding 7: `WORKSTEP_TYPE_PERM` covers 3 of 5 codes — calculating/confirm_release users silently regress from "see docs" to "403"
- **Severity:** Medium
- **Location:** plan.md L54 ("`bp_program_calculating` / `bp_program_confirm_release` không map workstep_type → user chỉ có 2 code này → list-doc empty. Acceptable?"); phase-04 L32
- **Flaw:** Plan defers this as "acceptable, raise in review" but doesn't verify CURRENT behavior for calculating-only users. Current list-doc: verb gate passes (calculating is in the 5-code `@RequirePermission`), `@RequireDataAccess(TABLE)` applies dataScope, service returns docs filtered by `applyDataScope` — calculating user sees docs at programs in their scope. New behavior: `resolveAllowedWorksteps` returns empty set (no workstep maps to calculating) → throws `ForbiddenException`. This is a silent feature regression: users who could see docs will now get 403. Plan calls it "acceptable" without confirming with product that calculating users should be blocked from list-doc.
- **Failure scenario:** User with only `bp_program_calculating` (e.g. a finance user in calculating phase) currently opens list-doc to review uploaded files → sees docs. After pilot: same call → 403. User reports "I can't see my documents anymore." Product didn't ask for this.
- **Evidence:** `src/modules/bi-payment/document/bi-payment-document.service.ts:19-24` (WORKSTEP_TYPE_PERM has 4 keys mapping to 3 codes; calculating/confirm_release absent); `src/modules/bi-payment/document/bi-payment-document.controller.ts:31` (5 codes in `@RequirePermission`); plan.md L54.
- **Suggested fix:** Before cook, verify with product whether calculating-only / confirm_release-only users should see list-doc. If yes: add a fallback in `resolveAllowedWorksteps` — if user has any of the 5 codes at program (via `getAccessibleRecords` for those codes too) but no workstep-mapped code, return ALL worksteps (treat as "program-scoped, no step restriction"). If no: explicitly document the regression in phase-04 and add a migration note for affected users.

## Finding 8: Brittle coupling between 5-code verb gate and 3-code StepScopeService — new code silently breaks
- **Severity:** Medium
- **Location:** plan.md L49 ("`@RequirePermission` list-doc giữ 5 codes (verb gate fast-fail; service là enforcement cuối)"); brainstorm L183 ("nếu sau này có code mới 'xuyên' vào list-doc, verb gate sẽ pass → service phải là rào chặn cuối")
- **Flaw:** Plan acknowledges the risk but defers mitigation to "test service kỹ." The 5-code list in `@RequirePermission` and the 3-code `WORKSTEP_TYPE_PERM` map are maintained independently with no compile-time link. If a 6th code (e.g. `bp_program_auditor`) is added to `@RequirePermission` later, verb gate passes, but `StepScopeService` only knows 3 workstep codes → auditor with only `bp_program_auditor` gets empty `allowed` → 403. The brittleness is structural, not testable away.
- **Failure scenario:** Future PR adds `bp_program_auditor` to `@RequirePermission` on list-doc (auditor role needs read access). Verb gate passes for auditor. `resolveAllowedWorksteps` iterates `WORKSTEP_TYPE_PERM` (still 3 codes) → auditor has none of those 3 at program → empty → 403. Auditor sees nothing. Bug is silent because no test links the 5-code list to the 3-code map.
- **Evidence:** `src/modules/bi-payment/document/bi-payment-document.controller.ts:31` (5 codes); `src/modules/bi-payment/document/bi-payment-document.service.ts:19-24` (3 distinct codes); plan.md L49.
- **Suggested fix:** Add a runtime invariant check in `StepScopeService` constructor: assert that every code in `WORKSTEP_TYPE_PERM` values is a subset of the list-doc `@RequirePermission` codes (via metadata reflection). OR add a unit test that reads `@RequirePermission` metadata and asserts `WORKSTEP_TYPE_PERM` codes ⊆ required codes. OR narrow `@RequirePermission` on list-doc to only the 3 doc-relevant codes (drop calculating/confirm_release) — but this is a separate product decision.

## Finding 10: Scale — 3N `getAccessibleRecords` calls unbounded for list-programs dashboard
- **Severity:** Medium
- **Location:** plan.md L55 ("N-query optimize → defer sau pilot + đo perf"); phase-04 L38 ("Perf đo: log time `resolveAllowedWorksteps` (3-4 getAccessibleRecords call)")
- **Flaw:** Plan defers optimization but doesn't check if a list-programs consumer exists that would trigger N×3 calls. `BiPaymentProgramService.search` exists (list programs with dataScope). If a dashboard calls list-programs then list-doc per program, that's 3 calls × N programs. For 50 programs: 150 Redis-then-DB calls. Plan says "Cache TTL 120s hấp hẫu" but each call is a distinct cache key (`perm:user:{uid}:da:bi_payment_programs:{code}`) — 3 distinct codes = 3 cache misses on first hit, then hits. But the N dimension (programs) doesn't benefit from cache because `getAccessibleRecords` returns ALL accessible programIds in one call — so actually it's 3 calls total regardless of N programs, IF the dashboard calls `resolveAllowedWorksteps` per program. Wait — it does call per program. So 3 calls × N programs = 3N. Cache helps on repeat calls for same user+code, but first dashboard load = 3N Redis calls.
- **Failure scenario:** Dashboard loads 50 programs → calls list-doc per program → 150 `getAccessibleRecords` calls. Even with cache, first load = 150 Redis GETs (misses) + 150 DB queries. At 5ms each = 750ms just for permission checks. User-visible lag.
- **Evidence:** `src/modules/bi-payment/program/bi-payment-program.service.ts:55-63` (search/list programs); `src/common/authorization/services/permission-cache.service.ts:41-57` (per-call Redis-then-DB); plan.md L55.
- **Suggested fix:** Plan should verify whether a list-programs-then-list-doc-per-program dashboard exists (scout `BiPaymentProgramController` consumers). If yes: add a batch API `resolveAllowedWorkstepsForPrograms(userId, programIds[])` that calls `getAccessibleRecords` once per code (3 total) and partitions by programId. If no consumer: keep defer, but note the threshold (e.g. "acceptable for ≤10 programs per page").
